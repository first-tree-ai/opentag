# GitHub platform integration

openTag owns its GitHub OAuth App, Slack, and Feishu credentials. The Server composes integration management, execution authorization, short-lived credential capabilities, and provider proxies. A trusted Runner gives native CLI processes execution-local handles.

## Identity and storage

A GitHub connection belongs to an Account and GitHub host, with one current OAuth connection. The nullable `oauth_client_id` identifies the configured OAuth App; the retained `app_id` identifies historical GitHub App rows. New OAuth rows have no `app_id`. The single `github_connections` table stores the encrypted access/refresh pair and one in-progress OAuth flow. Revoked and superseded rows retain identity and history. Historical repository JSON stays inert and absent from status DTOs. Existing IM tables retain Slack and Feishu credentials.

The one-time forward migration adds `oauth_client_id`, makes `app_id` nullable and updates old current App rows to revoked while clearing credentials, flows and worker claims. It preserves row IDs, original App IDs and historical data; it neither renames existing fields nor deletes rows. A shape constraint prevents old App rows from becoming current again. All users reconnect through the new OAuth flow, creating new connection IDs. Migration failure before commit rolls back atomically. After commit, recovery keeps the OAuth schema and repairs the new version; an old App binary cannot restore the cleared bindings. Stop old Servers/workers and drain in-flight GitHub work before applying the migration. Do not automatically replay writes or revoke existing GitHub grants/installations as part of this cutover.

Runtime Git, REST and GraphQL use the owning Account’s current connected GitHub OAuth App access token. The Server checks task/account/execution authority, obtains the current credential and rechecks authority before opening the upstream request. GitHub enforces that user's access, OAuth scopes and organization policy. The token stays on the Server: Sandboxes receive only execution-local handles. PRs and comments use the connected user identity; commit author, committer, bytes, object IDs and signatures remain unchanged.

GitHub API calls consume the connected user’s shared API budget. Runtime requests no longer derive/revoke a token or probe repository metadata for every operation. There is no additional token cache or repository authorization cache.

The owning Account's current connection determines the GitHub actor for admitted IM tasks, configured schedules and traceable Agent collaboration. An IM sender is not automatically a separate GitHub identity. The integration adds no operation audit trail, sender-account mapping or additional identity setting. The existing task-source records remain authorization facts.

The Agent chooses repositories, refs, PR heads/bases, merge/review operations and work across Sessions. Runtime forwarding does not parse GraphQL selections, keep node identities, plan per-operation permissions, or enforce code/Tree roles. Existing GitHub permissions and repository rules still apply. openTag maintains no extra repository whitelist.

## Invalidating access

GitHub authorization versions and credential generations serve different purposes. Scope changes, disconnection, and loss of authorization invalidate previously issued runtime access. A successful routine user-token refresh advances only the credential generation. Refresh and OAuth completion must compare the captured identity and version; a late response cannot reactivate a disconnected connection.

Refresh token consumption is not automatically retried after an uncertain response. A claimed refresh whose outcome is unknown requires reauthorization. A local credential-envelope failure is not an unknown outcome: nothing was sent to GitHub, so the claim releases untouched and the credential survives for a later retry. A periodic recheck that finds the access token already expired defers with a transient outcome; the refresh pass owns expiry recovery, and the expected 401 never clears a recoverable refresh credential. A credential-invalid response arriving at or after the access token's expiry defers the same way. A successful client-authenticated refresh persists the sealed rotated pair before any independent identity check; a later transient recheck failure retains that pair and schedules another check without replaying the consumed refresh token. A successful refresh also advances the recheck generation — never the authorization version — so a verdict minted against the old credential can never land on the new pair while runtime grants stay alive. Periodic rechecks scan all active due connections, without relying on App webhooks. Stale recheck results cannot overwrite a newer invalidation.

Periodic rechecks use `GET /user` with the access token and verify `X-OAuth-Scopes` for the required `repo` grant. They consume the user's API budget. Missing or malformed scope evidence is transient; an explicit missing `repo` scope or a user identity mismatch requires reauthorization. Client-authenticated check-token calls are reserved for OAuth callbacks to establish client ownership once. The default healthy recheck interval is five minutes. Worker scans and expired OAuth cleanup use batches of at most 100 rows. An expired OAuth sweep locks its bounded candidate set before clearing their flow fields in place without deleting rows.

IM retains its existing generation field as a conservative authorization epoch. Authorization changes advance it; observations and heartbeats do not. Slack authorization depends on both the binding and its installation. Agent suspension, restoration, and placement changes also invalidate execution through the existing Agent revision fence.

## Encryption rollout

Application encryption supports the existing v1 format and an authenticated v2 envelope with a key ID and caller-supplied binding context. IM remains on v1 writes by default. Deploy compatible readers everywhere before opting into v2 writes; keep all required decryption keys until their ciphertext has been migrated or removed. Reverting to a binary that only reads v1 is unsafe after v2 writes begin.

Bound contexts distinguish credential purpose, owner, and stable record identity. Changing an envelope's record, owner, purpose, key ID, or authenticated content must fail authentication. New GitHub credentials require bound encryption. Platform secrets must not be included in logs or upstream error messages.

OAuth persistence accepts synchronous credential factories. The service allocates the final connection and flow IDs before invoking encryption. Replacing a GitHub user encrypts against the newly allocated connection ID inside the same transaction; failure rolls the replacement back. Factories must not perform network I/O, and provider token exchange happens before the completion transaction.

## Management and execution

Configure `OPENTAG_GITHUB_OAUTH_CLIENT_ID` and `OPENTAG_GITHUB_OAUTH_CLIENT_SECRET` from the same OAuth App. Nonempty retired `OPENTAG_GITHUB_APP_*` variables produce a startup warning listing names only; they never enable the integration. Register the exact `${OPENTAG_PUBLIC_URL}/api/v2/integrations/github/oauth/callback` callback. Enable expiring user tokens; authorization uses PKCE and requests `repo offline_access`. A token response without access expiry, refresh token or refresh expiry is rejected. The Server verifies client ownership, scope and user identity before accepting a credential. Retired `/api/v1/integrations/github` routes, including callback, webhook and disconnect, return 410 before business writes. Old App events cannot mutate new OAuth connections. Native GitHub management lives in Account settings, after the personal profile and before conditional Cloud billing. Computer management remains in the account menu. Agent Connectors manage MCP mounts; there is no account-level connector directory or cross-Agent credential inventory.

Keep the OAuth Client ID stable for a database that has current OAuth connections. Replacing the OAuth App against those existing bindings is unsupported: reads and workers select the configured client, while current-connection uniqueness spans the Account and host. After changing the Client ID, the overview cannot see an old-client binding, Connect can return `GITHUB_CONNECTION_CONFLICT` (409), and Disconnect under the new client does not clear that binding. There is no automatic cross-client replacement, startup cleanup or data migration for this scenario. Any future App replacement needs a separately designed data transition before changing the deployment configuration. Rotating the secret of the same OAuth App, refreshing user tokens, or changing Server/Sandbox machines and IPs does not change the stored client identity. Independent databases have independent bindings. This limitation is separate from the supported one-time GitHub App-to-OAuth cutover above.

The GitHub section presents two independent settings: Account authorization and Repository access. Both are visible before account authorization, without numbered steps, completion checks, or health badges. Introductory copy describes account authorization and repository access; shared Agent scope is explained in help. Before account authorization, each setting is a compact label-and-action row without repeated explanatory copy. Authorize GitHub account and Configure on GitHub align at the right on wide containers and stack below their labels on narrow containers. The account setting otherwise shows the saved identity with directly visible Change/Remove controls. An incomplete initial authorization can be started again. A concrete Server requirement adds Reauthorize beside the identity and an explanation inside the same row. Initial loading, overview errors, and deployment unavailability keep their existing actionable feedback; internal pending/revoked/superseded lifecycle states are not shown.

Account identity and actions depend only on the management overview. The main settings page does not query repository discovery or infer organization roles or approvals. An active account offers View repositories, which opens a read-only dialog and starts fresh discovery with the Server-held current user credential. Closing aborts browser requests and clears the dialog data; the viewer is also keyed by connection ID, authorization version, and status. Returning from GitHub triggers a fresh read only when configuration was opened from a still-open viewer and the user actually left and returned. It never implies configuration success. An account OAuth callback explicitly reports account authorization only. GitHub owns the user/account chooser, OAuth consent, scope checks, organization approval and SSO authorization. OAuth access follows the user’s repository permissions; there is no installation or per-repository selection step.

Change starts the explicit replacement flow and retains the old authorization until replacement succeeds. Authorization and removal show progress at their initiating controls and prevent duplicate submissions. Authorization progress describes navigation to GitHub. A new operation clears the previous callback outcome. Removal requires confirmation naming the identity and shared Agent impact; it clears openTag credentials and native runtime access, without revoking the provider grant or uninstalling the App. Failed removal remains in its dialog for retry, dismissal clears its error, and cancellation returns focus to Remove. Results retain an accessible focus target without an empty visual row.

Unsaved display-name edits survive the full-document OAuth round trip in a bounded, Account-scoped, tab-local draft. Restoration requires the same Account and confirmed profile within 30 minutes; saved, discarded, consumed, or signed-out drafts are cleared. A failed authorization start or pre-navigation guard also clears the captured snapshot, so an abandoned edit cannot reappear on a later visit. Authorization checks the latest edit before navigation, including edits made while its request was pending. If the browser cannot retain a dirty draft, it stays on the page and asks the user to save or discard it. Authorization never implicitly saves the profile. Profile writes and refreshes must finish before leaving.

After account authorization, Repository access shows repositories available through that user's OAuth authorization. The viewer requires an active connection. Configure on GitHub opens `https://github.com/settings/applications` in a new tab with `noopener noreferrer`; it does not install an App or choose individual repositories. OAuth repository access follows the user's permissions and organization approval/SSO policies. openTag has no Agent assignments, repository delegation or extra Account allowlist. The retired bindings route returns HTTP 410 and cannot change retained JSON.

Discovery is display-only and bounded to 100 pages of 100 repositories. The dialog merges pages into 100-row batches, looks ahead before offering Load more and limits each interaction to ten requests. Filtering covers visible loaded rows. Failed continuation retains successful pages and retries its cursor; failed refresh retains old results with explicit stale feedback. Empty guidance points to account permissions and OAuth authorization. A truncated result remains visibly partial. Transient read failures do not imply revoked authorization. The existing responsive controls, accessible help popovers, close behavior and keyboard focus restoration remain unchanged.

The viewer sends its connection ID and authorization version with every discovery request. The Server checks that scope before opening the credential and again after upstream discovery; a changed scope discards the page instead of mixing repository results across GitHub account replacements. The two query fields are optional together for older callers. Explicit connection-state, missing-connection, or authorization-version errors re-read the authoritative management overview. A changed authorization closes the obsolete viewer and exposes the applicable account action with keyboard focus restored. Overview reconciliation failure preserves the saved identity and repository retry. Transient upstream repository errors never trigger account reconciliation or imply reauthorization. Closing the viewer prevents a late reconciliation response from changing account controls.

Every human sender accepted by an Agent's existing IM channel admission may request GitHub work using the Agent owner's Account connection, within that GitHub user's OAuth permissions. This is intentionally broader than Account-owner-only IM access; the IM sender is not mapped to a separate GitHub identity, and no GitHub-specific sender or repository allowlist is maintained.

Configured schedules qualify only through Server-recorded execution provenance. Creation, edits and Agent resume capture the current fenced execution's source; dispatch freezes that source on the message. A scheduler origin alone grants nothing. Legacy/autonomous schedules without a traceable human root keep running without GitHub authority, and Account pause/resume does not upgrade their provenance. Already-dispatched work retains its snapshot after schedule changes or deletion.

Collaboration similarly requires exact Server-recorded provenance from a live fenced execution: the Session CLI passes its nonsecret execution ID alongside its existing Session proof, and the Server stores the source on the message. Local commands read the current execution marker from the stable provider environment file on every invocation, even when a provider runtime is reused across turns; Cloud publishes the same marker in its per-turn file. Missing current material never falls back to a stale inherited execution ID. Old/untraceable collaboration, bot ingress, bare Session identities, and validation probes receive no GitHub authority. Repository lists are absent from execution metadata and prompts.

Local peers negotiate `runtime.githubUserTask: 1`; Cloud Runners opt in with `githubUserTaskVersion: 1`. Older peers without this opt-in retain login, IM, recovery and upgrade access but receive no GitHub provider. User-task-capable old peers retain their existing operations with a new Server. New data clients offer the `opentag-provider-http-v2` WebSocket subprotocol; a new Server replies with `httpVersion: 2` only to those clients. A new client connected to an old Server can still perform existing methods, but refuses HEAD locally with `github_protocol_upgrade_required`. Deploy Server before Runner/Local. Old Server behavior, including its cumulative request limit, persists until it is upgraded.

The two runtime capabilities are `runtime.runtimeCredential` and `runtime.providerProxy`. Opening an execution binds Account, Agent revision, accepted task source, Session placement, current Computer connection, and Cloud Sandbox generation. A guessed Session ID or unrelated IM sender is insufficient. The broker rechecks these facts before issuance, renewal, each request, and during streams.

- A Runner capability lasts 60 seconds and renews after approximately 30 seconds. At most current/previous capabilities overlap. Streams recheck platform account/connection/execution authority every five seconds. GitHub controls repository ACL enforcement on new requests; M1 does not promise five-second discovery of a GitHub repository ACL change during an already-open stream.
- The data WebSocket uses a single-use 15-second ticket in its first frame. Query strings, cookies, and bearer headers cannot authenticate this endpoint. Binary chunks carry at most 64 KiB plus a four-byte stream ID, with a 1 MiB credit window per direction. Consuming bytes replenishes credit. Completion races retain outstanding-byte bounds; future unknown IDs, reused open IDs and over-credit frames remain invalid. Frames outside the bounded retired history are inert.
- The Runner holds capabilities in memory. CLI-visible material contains only execution-local handles, a public CA, proxy addresses, and nonsecret IM metadata. No OAuth client secret, access/refresh token, Bot Token, tenant token, or Cloud control credential enters the Sandbox.
- IM proxy operations use registered Slack/Feishu routes and enforce the current binding and execution authority within the Bot's granted resource access. The current channel/thread is reply context, not an implicit exclusive destination allowlist. Every proxied write is one upstream attempt per proxy request, with no durable journal: JSON writes require both HTTP 2xx and explicit provider success evidence; explicit provider errors and definite 4xx (except 408) are rejections relayed to the caller; missing success evidence, 5xx, 408, timeout, transport failure, or an unparseable write response surfaces as an explicit `write_outcome_unknown` error. An ambiguous write is never automatically replayed — reconciling it against the platform is the task layer's responsibility, and a caller-initiated retry is simply a new proxied request. Upload-byte transfer is its own single-attempt write, separate from the provider's final attachment completion call.
- Local defaults to the existing IM credential mode. Set `OPENTAG_RUNTIME_CREDENTIAL_MODE=proxy` in the daemon launch environment to opt into proxy mode. Cloud requires proxy mode and never falls back to raw IM credentials.

Native command names and arguments remain `git`, `gh`, `slack api`, and `lark-cli`. Launchers supply execution routing and local handles automatically. GitHub business API authorization belongs to GitHub; the Agent channel cannot operate OAuth, App secret, credential inspection, token creation or revocation control endpoints. IM retains its registered routes and binding policy.

## Git and Context Tree

M1 implements the scope requested by the PR author, `@yuezengwu`: let Agents manage GitHub work across Sessions within the connected owner user/OAuth permissions, including tasks from existing IM admission, user-configured schedules and traceable same-account collaboration. There is no extra GitHub sender/repository allowlist or runtime Tree publication gate. The Agent owner is the GitHub actor; an admitted IM sender is not automatically that GitHub user. This records the requested behavior, not repository-owner or reviewer approval; those remain separate PR gates. It does not expand the platform execution/sandbox boundary.

Git smart HTTP is streamed byte-for-byte to GitHub. The runtime Server does not create a repository snapshot, execute Git, inspect pack objects, stage publication or rewrite commits. Arbitrary branches, tags, ref deletes, force pushes, multi-ref writes and cross-Session PR work are governed by the upstream GitHub user/OAuth permissions and repository rules.

Context Tree runtime Git/gh uses this same path. The Agent follows Tree skills and chooses when to verify, publish and recover. Settings connection verification, configured-target reconciliation, prepare/loading checks and the pinned verifier remain separate consumers with their existing limits. A successful GitHub push does not establish that Tree loading will succeed; a later load failure does not rewrite the earlier GitHub result.

Managed Context Tree preparation still requires current execution transport, including cached preparation, with no host-credential fallback. Local/Cloud settings verification retains its Account-authenticated, single-repository read-only operations and pinned verifier. The verifier uses the Account's full OAuth user token: its repository and read-only limits are enforced by Server target checks and verifier helpers, not by a narrower upstream GitHub credential. The token itself can access every repository and write operation permitted by its OAuth grant and user permissions. Those management-only leases and Git helpers remain available; normal Agent requests never use them. Creating a Tree repository keeps its existing capability boundary.

## Native HTTP transport

The Server forwards REST and GraphQL methods, opaque query strings and business bodies without API/field allowlists or response rewriting. Raw Node HTTP preserves compressed bytes, content encoding/length, pagination, conditional/range headers, native status codes and GraphQL partial errors. It does not manufacture schema/Projects responses or remove arbitrary business fields named `token`. Optional Projects permission errors can stop unrelated PR edits in gh 2.91.0; the tested gh 2.100.0 handles them natively. Record the actual tool version when diagnosing this difference rather than rewriting GraphQL results.

Authenticated upstream destinations remain fixed to HTTPS `api.github.com` and Git smart HTTP on `github.com`. Caller credentials, cookies, hop-by-hop and internal headers are removed. The Server uses the current user token as the HTTP Basic password with username `x-access-token` for Git, and Bearer authentication for REST/GraphQL. This distinction is tested against a Basic-only Git upstream, rather than an API-style fixture. DNS addresses are checked and pinned before connection with normal TLS hostname verification.

GET/HEAD downloads may follow up to five validated redirects from these fixed origins. `http-target.ts` accepts the exact results receiver, release-assets, objects and codeload hosts, plus the anchored numeric `productionresultssa[0-9]+.blob.core.windows.net` Actions shard family. GitHub documents the [Actions storage family](https://github.blog/changelog/2023-01-31-github-actions-job-summary-updates/) and [download domains](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). This replaces the single observed `sa13` account after real artifact/job-log redirects used `sa9`; it does not accept arbitrary Azure/S3 hosts or provide new initial proxy destinations. Every hop keeps HTTPS/443, public DNS pinning and TLS checks. Cross-origin credentials are stripped and never restored, including if a later hop returns to the API. Unknown download destinations fail explicitly. Writes are never automatically retried or redirected: preserve their native status/body and omit an unsafe or cross-origin Location. Complete upstream errors are preserved; DNS, TLS, connection, timeout and truncated-response failures use closed diagnostic codes without credentials or signed URLs.

Active concurrency and byte-credit windows remain bounded. Completed stream bodies/authority are released, at most 256 small retirement records remain, and monotonically increasing IDs prevent reuse. There is no cumulative 256-request ceiling. At capacity only a new stream is rejected, leaving existing streams alive. Frames beyond the bounded retired history are inert; recent duplicate terminal/over-credit frames and reused open IDs are invalid. Idle upstream waits are bounded, but slow consumers do not start an absolute transfer deadline.

Local native `gh` on macOS and Linux uses the official `http_unix_socket` transport with a private, execution-owned socket and config. A custom temporary directory that exceeds the Unix socket path limit falls back to a private directory under `/tmp`. The adapter accepts only `api.github.com`, authenticates the local handle, and forwards through the same Relay and Server policy; closing the execution removes the socket. No system trust-store changes or TLS-verification bypass are used. This native Local `gh` contract covers macOS/Linux; Windows is outside its support and CI coverage. Cloud keeps its existing in-sandbox CONNECT/CA bridge; parent-local socket paths are never published to a Cloud Sandbox. Slack-only CLI flags and config are emitted only for Slack executions and validation.

Local native Git 2.47+ uses libcurl's `socks5h://localhost/path/to/socket` transport into a second execution-private socket. Like native gh's IPC, this carries HTTP only within the private Unix channel: SOCKS accepts only domain `github.com`, port 80 and CONNECT, never DNS resolution, TCP dialing, IP targets, BIND or UDP. The launcher applies a process-local rewrite of canonical `https://github.com/` URLs; stored remotes remain HTTPS. The fixed GitHub origin, local-handle authentication, Relay, Server execution policy and upstream GitHub HTTPS remain unchanged. This avoids macOS TLS-backend/keychain differences without adding a trusted CA or disabling TLS verification. Both sockets are exact Codex profile grants and are removed on execution close. Older Git keeps the existing authenticated HTTPS CONNECT route, preserving Claude Code and unrestricted Local compatibility; restricted Codex still denies that TCP route and needs Git 2.47+/libcurl 7.84+ for private IPC. Cloud keeps its existing CONNECT bridge and receives neither parent socket path. See libcurl's [Unix SOCKS proxy support](https://curl.se/libcurl/c/CURLOPT_PROXY.html).

Git launchers convert injected `GIT_SSL_CAINFO`/`GIT_SSL_CAPATH` values into generic Git config and then unset the environment overrides. Non-GitHub origins retain the caller's CA file/directory; GitHub HTTPS keeps its more specific execution CA and CA directory. The HTTPS CONNECT/Cloud paths keep TLS verification enabled.

Generated `gh` config includes its current schema version before publication, including the read-only Cloud mount. This prevents startup migration writes even for `gh --version`. A network-restricted Local Codex run receives only its execution's GitHub Unix socket through an acknowledged, ephemeral permission profile. The managed network controller uses limited mode with no allowed domains or local TCP bindings; unrelated sockets and direct TCP remain denied. Socket exceptions rotate with each execution and are removed before a later run without GitHub. Unsupported Codex permission profiles fail closed instead of running with an unconfirmed sandbox. GitHub stream-open failures preserve bounded reason codes as JSON (for example, `scope_denied` with HTTP 403); unknown failures remain 503 and raw errors are never returned.

Only the Local managed `gh` child sets `XDG_CACHE_HOME`, pointing inside its existing private socket temporary directory. Native log caches are reusable within that execution and removed by the adapter's existing close cleanup, including replacement and revocation. The Agent environment, Git and other CLIs keep their own cache settings. Cloud retains its scratch HOME and existing cleanup; no cache is added to workspace continuity or managed by a separate cache layer.

Checks, Actions, Commit statuses, PR operations and other GitHub business APIs use the same connected user credential. OAuth scopes, user permissions and organization policy must cover the intended operation; the proxy neither adds permissions nor converts permission failures into successes. Private-repository acceptance is required: a public read cannot prove private access. The separate Tree settings verifier pins its repository and read-only operation; OAuth cannot mint a narrower GitHub token.

`GitHub Native Proxy` CI downloads the official Runner-pinned gh and exercises real Git clone/fetch/push with preserved commit objects in macOS Local Codex IPC and Linux Cloud publication/CONNECT, plus native gh workflow discovery/commit filters, PR command lifecycle and cold-command authorization controls. These offline fixtures have no real provider credentials or GitHub side effects; they do not establish deployed user identity or commit-author acceptance.

Execution loopback certificates include explicit key usage and the TLS server-authentication EKU required by Apple's trust evaluation. Native macOS regressions retain the runner's default Git/TLS backend and additionally exercise SecureTransport for CONNECT and caller CA routing, including a missing-anchor negative control. Before HTTPS-dependent macOS tests, an independent plain `curl --cacert` probe checks a valid private anchor without openTag code or configuration; only a TLS verification failure (exit 60) produces an explicitly reported capability skip. Other probe errors and product failures still fail. Modern IPC tests never use this skip. Legacy CONNECT retains the existing platform TLS constraints: it is no worse than main, but success with private file anchors is not demonstrated on macOS 15 system libcurl. Linux/OpenSSL and capable macOS hosts exercise the full CONNECT and CA-routing cases. These tests do not change product backend selection or system trust. See Apple's [TLS certificate requirements](https://support.apple.com/en-gb/103769).

## Deployment and persistent state

`createPlatformRuntime` is the Server assembly entry. The Server image includes Git and the pinned Tree verifier. PostgreSQL is the only persistent integration state: GitHub connections and IM credentials recover from the database across a Server rebuild. There is no Server-local control volume, no file-backed write journal, and no separate persistent source ledger — rebuilding a Server never requires restoring an integration-specific disk. Short-lived capabilities, tickets, URL handles, and execution state live in bounded Server memory and end with the process; after a restart the Runner re-authorizes from current database facts. A restart or execution close never revokes the shared Account user token.

Only Tree settings verification keeps bounded temporary Git workspaces and bounded Server-local credential references (at most eight requests per verification execution and 256 executions). Releasing a reference does not revoke the shared OAuth token. Normal GitHub runtime forwarding allocates neither. These workspaces are private verification aids and never Sandbox mounts or authoritative state.

User-task provenance in Session messages and schedules is ordinary PostgreSQL task state. Cross-restart provider-operation ledgers and provider-result provenance tracking are explicitly withdrawn. The proxy performs one upstream write attempt per request; IM classifies outcomes and GitHub preserves native HTTP results and explicit transport failures; it does not promise persistent cross-restart resource blocking or exactly-once provider effects. If a product requires remembering an unresolved write across a crash, that is durable business state that must be modeled explicitly in PostgreSQL with real ownership and retention semantics, never a sidecar file store.

Cloud control identity belongs to Computer/Cloud orchestration; its integration with this credential runtime remains to be wired. The integration runtime only consumes an explicitly injected trusted verifier and activity checker (`TrustedCloudControlAuthority`): it keeps the credentialId/computerId/installationId binding, the current database Computer identity (`kind = 'cloud'` with the live installation identity), and per-request revocation checks. The current default startup injects no trusted Cloud control verifier or activity checker, so Cloud control authentication and Cloud credential activity are rejected; Local keeps its existing machine-token path and its Local-only restriction. There is no implicit self-issued Cloud credential, no Local-token fallback, and no additional file-backed Cloud credential database beyond the PostgreSQL-managed integration credentials. Executions remain bound to their exact current control connection; this correction does not provide stateless multi-node execution routing.

`CloudSandboxCredentialBridge` is the Linux command boundary for the Cloud orchestrator. It creates the Relay outside the command container and mounts only a public per-execution socket directory plus the workspace. The container runs as UID 10000 with no external network, no capabilities, a read-only root, resource limits and writable temporary directories. Control loss kills the command container; an execution cannot be replayed. It requires a trusted Linux Docker controller; a macOS host socket bind is not equivalent. The bridge supports later Cloud Sandbox orchestration and does not provision a cloud service or an LLM network path itself.

## Credential lifetimes

M1 preserves existing execution (24h) and MCP/Web (6h) lifetimes; unified renewal is a separate M2 design.
