# Cloud billing MVP

Cloud billing is optional and disabled by default. Local Agents keep their existing provider credentials and execution path. Hosted cloud completions and Cloud Agent connectivity probes use prepaid Account credit when billing is enabled.

The private `@opentag/cloud-billing` package owns pricing, Stripe Checkout, encrypted per-Account OpenRouter keys and durable credit records. It runs inside the cloud server and uses the same PostgreSQL database URL. OpenRouter meters token usage and cost. The public repository owns the module interface, authentication, cloud forwarding, Account UI and database schema/migrations. Public builds have no dependency on the private package when billing is disabled.

The production cloud image contains the private package's code and may be public. The private source repository does not make bundled code secret; provider credentials and pricing configuration remain runtime settings. A private image can be adopted later without reintroducing a separate service.

## Enable

The public Docker workflow builds a cloud image containing the application and its pinned private billing package. Set `OPENTAG_CLOUD_BILLING_ENABLED=true` alongside the existing Cloud Runner and cloud model configuration. Add the billing package's encryption, OpenRouter management, Stripe, pricing and welcome-credit settings to the application in CapRover. There is no billing URL, service token or separate database credential. Set `OPENTAG_AUTO_MIGRATE=true`: application startup applies the public Drizzle migrations before initializing billing. Billing tables live in the `billing` schema and reference `public.users.id`.

Stripe's signed webhook endpoint is the application's `/stripe/webhook`; Checkout returns to `/account` on `OPENTAG_PUBLIC_URL`. Follow the private checkout's README and the deployment instructions below, and use Stripe test mode before accepting real payments. The model catalog remains the existing Server-owned Router catalog with approved OpenRouter model IDs and capabilities.

Account shows one available USD credit balance, including the starting allowance and paid top-ups, and a custom-amount top-up form ($10–$1,000, in cents). The UI does not display pricing details or individual billing records. View usage opens account-wide cloud model-call totals, total tokens, and a daily chart for 1, 7, 30, or 90 days. These totals come from all recorded cloud calls in the billing ledger, including connectivity probes; local usage is excluded. Unknown token counts remain unmeasured and are identified as partial data. Checkout redirects back to Account; only a verified paid Stripe webhook adds credit. Payment recording does not depend on OpenRouter availability; the background worker reconciles key access and each new request checks the durable balance and payment blocks. Balance reads use stored credits and known spend without calling OpenRouter or provisioning a key. They can briefly lag provider metering; cloud admission still synchronizes before allowing spend. The balance refreshes automatically while payment fulfillment is pending. The welcome grant is a one-time USD allowance, so its token quantity depends on the chosen model.

The server resolves Account ownership from the authenticated user for balance and checkout, and from the verified Sandbox/Session/Agent relationship for executions. Browser mutations retain the existing CSRF protection. Hosted connectivity tests use the caller's authenticated Account. When billing is enabled, a billing module failure refuses cloud requests without falling back to a platform key. Turning the billing switch off deliberately restores the existing unmetered cloud path; keep it enabled once selling credit.

## MVP limits

This release uses manual prepaid USD top-ups, one fixed cost multiplier, and one welcome grant per Account. It includes duplicate-payment protection, encrypted keys, durable usage records, missing-generation reconciliation, and refund/dispute blocking for operator review. The pricing multiplier is immutable for this billing database. No auto-recharge, subscriptions, strict request reservations, billing admin UI, automated refund review, or mechanism for changing markup over time is included.

Credit consumption uses the greater of OpenRouter cumulative key usage and summed reported request charges, with persisted observed spend. Finalized request costs drain credit while cumulative usage catches up; cumulative usage also covers interrupted streams. Missing per-request costs are reconciled independently of token statistics. A valid cost is recorded even if counts are unavailable; unknown counts remain partial data rather than causing indefinite retries. Account synchronization and failed generation lookups use durable exponential backoff from 30 seconds to one hour, allowing newer records to progress. New credits, payment blocks and usage make the affected Account eligible for immediate synchronization. Streaming writes persist the first generation identity and changed usage rather than every token chunk. Overrun is absorbed by OpenTag and does not become customer debt. Concurrency, output, body, response, and timeout limits constrain exposure, but do not guarantee a fixed dollar overrun ceiling across models or provider-metering delays. Validate that exposure with the production catalog in Stripe test mode before enabling real payments.

Public request validation and output-budget clamping are shared by the cloud proxy and billing package. Transport bounds use the existing application settings `OPENTAG_CLOUD_MODEL_MAX_REQUEST_BYTES`, `OPENTAG_CLOUD_MODEL_MAX_RESPONSE_BYTES` and `OPENTAG_CLOUD_MODEL_REQUEST_TIMEOUT_MS` (defaults: 8 MiB, 16 MiB and 600 seconds); connectivity probes pass their shorter limits. There is no separate billing transport configuration.

See [OpenRouter limits](https://openrouter.ai/docs/api_reference/limits) and [Stripe fulfillment](https://docs.stripe.com/checkout/fulfillment) for the provider behavior this integration relies on.

## CapRover deployment

Deployment stays in the public OpenTag repository and uses the existing `Docker`, `Deploy Staging` and `Deploy Runner` workflows. There are no private deployment workflows, separate cloud release manifests or deployment-authority settings. `cloud-billing.json` pins the private package to an exact commit; updating that file is how a billing change ships with the application.

Configure the public repository secret `OPENTAG_BILLING_READ_TOKEN` with read-only Contents access to `first-tree-ai/opentag-billing`. Only the trusted main commit-image job checks out private source, without persisting its credential. It runs the pinned package's checks and tests against the application being built, then bundles it into the ordinary `ghcr.io/first-tree-ai/opentag:<application SHA>` image. The image records both application and billing revisions. Pull-request builds and the default local Docker target do not need private access. They build the application without billing; trusted builds use the `cloud` target and a named `billing` build context. Runtime provider credentials never enter the build.

Keep the existing public CapRover/GCP environment credentials. Configure billing secrets on the same CapRover application, using Stripe test keys in staging. Enable cloud identities, cloud models, billing and automatic migrations. The existing staging flow waits for the application image and CLI/Runner publication, deploys the application, then activates the matching Runner. The Runner helper reads the billing pin from the selected application commit, including on a manual rollback, and requires `/cloud-readyz` to prove both source revisions before activation and afterward. Billing initialization failures prevent activation. Ordinary `/readyz` remains independent so billing outages do not take local usage offline. Migrations still run during application startup.

Use one application replica, no predeploy function and stop-first replacement. In CapRover's service update override, set `UpdateConfig` to `{"Order":"stop-first","Parallelism":1,"FailureAction":"pause"}`, `RollbackConfig` to `{"Order":"stop-first","Parallelism":1}` and `TaskTemplate.ContainerSpec.StopGracePeriod` to at least `(OPENTAG_CLOUD_MODEL_REQUEST_TIMEOUT_MS + 30000) * 1000000` nanoseconds. The default 600-second timeout requires `630000000000`. The Runner helper verifies these requirements because billing admission locks are process-local. Replacement can briefly interrupt cloud service. Do not override `OPENTAG_BUILD_REVISION` or `OPENTAG_BILLING_REVISION`; they come from the image.

Register Stripe events `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `charge.refunded` and `charge.dispute.created` at the application's `/stripe/webhook`. Retain and separately back up the encryption key across releases. Back up the entire shared PostgreSQL database. Application startup requires an exact migration journal, so an older image cannot roll back migrations already applied; prefer a forward fix. Keep billing enforced once selling credit. These files do not configure or deploy a live environment.
