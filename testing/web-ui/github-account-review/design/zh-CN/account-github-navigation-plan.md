# 账户设置与原生 GitHub 访问方案

状态：2026 年 10 月 14 日提出的界面与交互方案，10 月 19 日复核并移除不必要的连接术语与状态展示。用户已确认下文两项范围排除，其余细节为待评审方案。本次没有修改产品代码。[英文原文](../account-github-navigation-plan.md)。

## 范围与依据

- 不新增账户级连接器一级入口。
- 不汇总所有 Agent 的凭据。
- Computer 管理保留在左下角账户菜单。
- 现有 MCP 连接仍在 Agent 的连接器页面管理。
- 当前原生 GitHub 作为账户拥有的专用代码访问能力处理，直接命名 **GitHub**，不引入“应用与服务”“集成”“共享连接器”等新导航。

区别依据是用户配置的对象及修改的影响范围。MCP 挂载配置某个 Agent 的工具；原生 GitHub 为符合条件的 Agent 任务提供账户级代码访问授权。界面不需要教授实现协议，也不预先决定所有未来 integration 的归类。

## 核对的实现基线

本次复核基线为本地可用的 `origin/main` 提交 `900ffead`，标题为 `fix(client): keep Local gh cache in execution temporary storage (#916)`。工作区检出较旧，因此使用 `git show origin/main:<path>` 核对当前主线，而没有将工作区旧文件视为最新实现。

- `apps/web/src/features/account/account-page.tsx` 包含个人设置、有条件启用的云端账单及 `GitHubIntegrationSettings`。
- `apps/web/src/features/account/github-integration-settings.tsx` 已有部署可用性、连接状态、授权意图、断开及安装发现。
- `apps/web/src/features/mcp/mcp-page.tsx` 管理 MCP 定义和 Agent 挂载，未包含 GitHub。
- `apps/web/src/routes/_authenticated/_resources/_shell/agents.$agentId.integrations.tsx` 将历史 Agent 集成链接重定向到 `/account`。
- `packages/shared/src/github-management.ts` 已提供可用性、连接状态、create/reauthorize/replace、安装元数据及分页仓库发现。安装 DTO 没有“待管理员批准”字段。
- `packages/server/src/api/github-integrations.ts` OAuth 只返回固定的账户或历史 Agent 页面，目前没有 Task 返回页面。
- `packages/server/src/services/github-proxy/github-provider-adapter.ts` 原生 Git、gh 操作使用连接用户的凭据。本方案不改变运行时授权策略。
- `github-management-service.ts` 将移除操作交给 `github-connection-service.ts`，清理本地凭据并使本地授权失效。这个操作不会调用 GitHub 撤销上游授权或卸载 App。操作名称必须描述从 OpenTag 移除，不能声称在 GitHub 全面撤销。

## 用户任务与术语

用户管理的是 GitHub 身份与仓库访问权限，不需要维护一条被持续监测的 GitHub 连接。反复出现的问题是：使用哪个 GitHub 账户、在哪里修改仓库访问权限、如何更换或移除这个账户。

使用 **授权 GitHub**、**GitHub 账户**、**仓库访问权限**、**更换账户**、**移除账户**。不把“账户已连接”简单替换成常驻的“已授权”“正常”“就绪”标签；展示已保存的身份就足够了。授权完成也不能证明当前拥有每个仓库及每项操作的权限。

保留服务端 pending/active/reauthorization_required/revoked/superseded 等安全与并发控制所需的生命周期，但不把它们变成用户要理解的一套状态分类。只有说明某次操作结果或用户需要采取的具体行动时，才增加提示。

保留现有目的地与历史重定向。不建设 `/integrations` 集中页面、账户连接器页面，也不将原生 GitHub 加入 MCP 发现目录。全局页面使用现有窄导航轨道；Agent 页面使用完整侧栏。账户设置不保留某个 Agent 的选中导航。

完整侧栏的账户触发器已经显示用户名，因此弹出菜单只展示操作，不重复资料块。窄导航只有头像时，可以在菜单顶部展示一个不可点击的身份块：用户名及次要邮箱。两项身份字段均不作为菜单操作。

## 账户设置

采用单列内容，最大宽度约 740px。沿用现有暖色页面背景、白色 SettingsList、轻分隔线与紫色操作色。无需设置子导航或卡片嵌套。

### 个人设置

- 显示名称可编辑，发生修改后才显示取消与保存。
- 邮箱作为只读次要文本。
- 语言沿用现有选择器及行为。
- 保留当前“保存成功、账户刷新失败”处理：已保存名称不能回退，提供重试刷新，不重复保存。
- GitHub 操作不能重置未保存的个人资料。前往外部授权可能丢失修改时，应保存本地草稿，或在离开前明确处理修改，不能静默丢失。

### GitHub 区域

区域标题直接为 **GitHub**，与“个人设置”同级，紧随其后。说明文案：“供你的所有 Agent 使用。” 只交代影响范围，不重复账户及代码任务的含义。展示已保存的登录身份，不增加状态标签或绿色指示点。

通常的配置界面在一个 SettingsList 内提供两行：

1. 账户：`@login`、锚定在身份行的更多操作。
2. 仓库访问权限：**在 GitHub 管理**，新标签页打开 GitHub，保留外部链接图标。

沿用现有 SettingsList/SettingsRow，个人设置与 GitHub 的值列对齐。标题放在列表外，只保留一层分组列表，不再给整个区域套一层有边框卡片。沿用现有区域标题字号、14px 行文字，桌面单行行高约 64–68px，不做放大的集成卡片。手机将标签和值上下排列，并保留足够的触摸目标。

当前 DTO 提供 GitHub 用户名，没有头像地址。以用户名表示身份，不伪造与 OpenTag 资料相似的彩色首字母头像。未来有经过验证的 GitHub 头像时，可按识别价值补充，不增加账户状态。

更多操作只包含“更换账户”“移除账户”，通过所在行明确 GitHub 语境。服务端明确要求用户更新授权时，才提供重新授权。移除只在操作菜单和确认框中使用危险样式。菜单不放在区域标题旁，以免被误解为同时管理仓库访问权限。

可选的仓库说明紧邻“仓库访问权限”，通过有名称的帮助控件点击或触摸展开在本行，不在区域下方常驻一条公司仓库 FAQ。重要操作不依赖悬浮。沿用现有 DropdownMenu、Popover/Collapsible、Dialog，需要时使用 portal，避免被 SettingsList 的 overflow 裁切。

“在 GitHub 管理”使用现有服务端拥有的安装跳转，不根据安装 ID 自行拼 GitHub URL，也不承诺 API 尚未提供的安装直达页面。普通账户设置不复制安装列表、仓库数量或权限健康面板。用户在 GitHub 选择所属账户或组织及仓库。

仓库发现结果是快照，不是运行时授权证据。移除常驻“刷新”，因为它容易暗示一次无法证明任务权限的健康检查。具体任务需要发现信息时，从 GitHub 返回后自动更新，并在现有任务继续流程中验证访问。发现读取失败不能抹掉独立加载的已保存身份。只有某次操作失败时才在旁边提供重试，并遵循限流提示。分页或截断时，不把部分结果呈现为完整总数。

云端额度仅在启用时显示，位于 GitHub 之后；充值与用量入口留在区域内，保留现有独立用量目的地。账户菜单不增加默认账单入口。

## 授权与仓库访问权限流程

### 首次授权

1. 没有保存 GitHub 身份时，展示简短说明和“授权 GitHub”。不增加“未连接”或“未授权”标签。代码任务也进入同一个区域。
2. 调用现有授权开始 API，使用 create 意图；授权 URL、state、PKCE、过期时间由服务端提供。
3. 当前标签页前往 GitHub；需要时保存安全的本地返回上下文及个人资料草稿。授权按钮无需使用仓库管理的新窗口／外部链接图标。
4. 回调返回账户设置，重新获取账户授权并展示身份。简短成功反馈只描述本次操作，不宣称持久的连接健康。
5. 保留“在 GitHub 管理”，供用户设置或调整仓库访问权限。任务已报告访问失败时，指明目标仓库及操作；单独的空发现结果不触发账户级警告。
6. 返回后自动更新任务所需元数据，通过现有支持的方式回到原任务继续；账户页不宣称任务权限已经就绪。

用户需要指引时才解释身份授权与仓库选择，不要求所有人理解两个永久设置状态。未完成流程被取消或过期时，回到原界面并给出可重试的简短结果。数据库存在 pending 行，不等于要长期显示“继续连接”模式；重新开始应由服务端创建新的有效授权流程。

### 公司仓库

说明 App 安装或配置在目标仓库所属的个人账户或组织，用户也必须有相应 GitHub 权限。组织所有者及政策允许的仓库管理员可安装或配置；成员可能需要申请。已有组织安装时，仅为访问组织仓库无需额外安装到个人账户。[GitHub 安装要求](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party)、[申请组织安装](https://docs.github.com/en/apps/using-github-apps/requesting-a-github-app-from-your-organization-owner)

提供可选的“公司仓库授权说明”。具体操作无法访问已知目标时，指明该仓库，解释可能需要调整账户或 App 权限。不能从不完整列表推断无权访问，也不能用空发现结果虚构持久的“等待管理员批准”状态。

### 重新授权与切换

重新授权使用现有 reauthorize 意图，恢复同一身份。“更换账户”使用明确的 replace 意图，直接进入 GitHub 授权，不增加前置确认。区域说明已经交代共用范围，当前实现也会在新授权完成前保留旧凭据。取消或失败时保留原身份，不能仅因选择了菜单操作就先移除它。

“移除账户”使用一次标准模态 Dialog，不在设置下方追加确认卡片。指明具体用户名，说明所有 Agent 后续无法再通过该授权访问 GitHub，进行中的代码任务可能受影响。次要说明交代只移除 OpenTag 保存的授权，GitHub 侧授权及 App 安装会保留。按钮为“取消”和危险操作“移除账户”。不能称为“撤销 GitHub 授权”，因为当前接口清理的是本地授权，不会撤销上游授权。不解除 MCP 挂载，也不撤回已完成的 GitHub 操作。成功后回到“授权 GitHub”界面，不展示“未连接”标签。

## 任务中的入口与返回

不在所有 Agent 概览或 MCP 列表常驻 GitHub 控件。仅在原生 GitHub 操作返回可处理的访问问题时，展示紧凑的任务操作提示。

没有保存身份时：“授权 GitHub 以访问 first-tree-ai/opentag。” 具体操作报告仓库访问权限不足时：“无法读取 first-tree-ai/opentag，请在 GitHub 检查仓库访问权限。” 不统一要求重复 OAuth。账户授权操作进入 `/account`，定位并聚焦 GitHub 区域，携带经过验证的来源上下文；仓库管理可以直接打开现有服务端拥有的 GitHub 跳转。账户设置显示“返回任务：修复登录失败”。

使用同一个账户设置区域，不创建 Agent 拥有的 GitHub 设置表单。消息渠道发起的任务也可通过恢复链接进入网页，并在登录后保留来源 Agent、Task。

现有 OAuth 回调不能直接返回 Task。最小扩展是在固定账户回调外增加安全的前端返回上下文：

- 在标签页 session storage 保存带版本的账户、来源 Agent、来源 Task 标识、授权意图及过期时间，不存凭据或任意跳转 URL。
- 使用 typed helpers 验证目的地，检查当前账户权限，依据授权生命周期过期处理；退出登录、切换账户及完成或取消后清理。
- 回调通过验证并获取最新服务端状态后，恢复来源返回入口；仓库访问仍未配置完成时，留在 GitHub 区域。
- 上下文缺失或过期时，正常停留在账户设置。

授权完成不自动重放中断的 push 或 PR 创建。返回既有任务继续流程；任务已经失败而非可恢复暂停时，应明确使用当前支持的继续机制，不能暗示现有实现已经支持 Pause/Resume 协议。

## 展示与问题处理规则

普通设置展示已保存的事实和管理操作，不展示生命周期标签、安装健康汇总或状态检查清单。

- 加载身份时保留行布局并显示小型占位，不在加载完成前闪现授权按钮。
- 服务端明确要求重新授权时，保留已知用户名，增加“需要更新 GitHub 授权”和“重新授权”操作。确认恢复后移除提示，不额外给身份增加状态标签。
- 任务操作失败时指明仓库和操作，提供对应权限管理动作。安装被暂停，仅在它影响当前任务时说明。仓库发现本身不能支持超出证据的权限结论。
- 取消、过期、请求失败及并发变化，作为当前操作的可重试反馈；保留仍然有效的原身份。临时 GitHub 请求失败不等于账户被移除或授权过期。
- 部署可用性属于能力开关，不是用户管理的 GitHub 状态。不可用时只给一条简短部署说明，不加标签或不可用的授权按钮。

使用有限的公开错误码分类，不依赖任意上游错误文本。归属、来源证明或运行时策略失败，不能一律靠重复 OAuth 处理。这些规则覆盖内部生命周期情况，但不要求用户学习它们的名字。

## 响应式与可访问性

- 桌面：沿用 240px Agent 侧栏、72px 全局窄导航，账户内容约 740px；页面标题 28px、主要文字 14px、现有紧凑控件尺寸。
- 手机：沿用紧凑顶部栏，资料标签、控件及仓库操作纵向排列。输入文字至少 16px，触摸目标约 44px。
- 产品表面保持不透明，更多菜单和确认框位于内容上方。关闭后焦点回到触发器，结果通过 status/alert 宣告。
- 从任务打开账户设置时定位并聚焦 GitHub 区域，保留可见返回操作及浏览器返回行为。

## 实施边界与验收

重构账户 GitHub 内容及安装操作，路由保持薄层，正常生成路由，使用 shared/browser 公共导出和 `m.*()` 文案。保留历史重定向。运行时授权、凭据存储与 Agent MCP 身份归属不属于本界面方案的修改范围。

任务恢复操作、前端 OAuth 返回上下文，以及将身份加载与任务所需的仓库发现解耦，属于界面工作。现有 API 已支持账户授权意图、本地移除、安装跳转、仓库发现。撤销 GitHub 侧授权、可靠审批状态或自动任务恢复需要另行设计契约，不属于本方案。

验收包括：

1. 账户菜单没有新增连接器、集成或账单入口，电脑仍可进入。
2. Agent MCP 列表和发现目录不加入原生 GitHub。
3. 普通账户设置与任务恢复使用同一个 GitHub 区域。
4. 普通设置只展示身份及权限管理操作，没有已连接、已授权、就绪标签，没有仓库数量、安装清单或常驻刷新。内部生命周期只产生必要的操作反馈，仓库发现失败不抹掉已保存身份。
5. 取消更换保留旧身份；移除作用于正确的 OpenTag 账户，不改变 MCP 挂载和 GitHub App 安装，也不声称撤销 GitHub 侧授权。
6. 同标签页 OAuth 后可返回来源 Task，拒绝过期、跨账户或任意目的地，不重放写操作。
7. GitHub 界面变化不破坏未保存资料，以及保存成功但刷新失败的处理。
8. 验证键盘、屏幕阅读器及 320/390/768/1024/1440px 布局。
9. GitHub 与账户页保持一致的标题层级、分组列表样式及值列对齐。仓库帮助属于仓库行，账户操作属于身份行。更换账户无前置确认，移除只有一次准确说明范围的模态确认并恢复焦点。

实施时运行受影响的账户、GitHub、侧栏、MCP 和返回上下文测试；提交 PR 前按 AGENTS.md 执行完整检查。本方案及效果图不代表产品已经实现新的 Task 恢复流程。
