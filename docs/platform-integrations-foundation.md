# Platform integration foundation

OpenTag owns its GitHub App, Slack, and Feishu credentials. The Server composes integration management, execution authorization, short-lived credential capabilities, and provider proxies. A trusted Runner gives native CLI processes execution-local handles. [简体中文](./zh-CN/platform-integrations-foundation.md)

## Identity and storage

A GitHub connection belongs to an Account, GitHub host, and App. There is one current connection in this namespace. Revoked and superseded connections retain nonsecret history. The single `github_connections` table stores the user's encrypted access/refresh credential pair, one in-progress OAuth flow, and retained historical repository JSON. The historical repository fields are inert: current services neither select nor mutate them, and status DTOs omit them. Existing IM tables remain the credential store for Slack and Feishu.

GitHub user credentials establish the user's repository admission on the control plane. Git and repository operations use App installation access tokens (IATs). The Server installation-token client requests one repository and explicit permissions, validates the resulting scope, and supports revocation. It is an internal transport adapter, not an authorization decision. A caller must establish Account, Agent, repository, and execution authority before minting a token. Neither user tokens nor IATs may be returned in a management response or sent to a Sandbox.

Each request identifies its actual repository by Git URL, REST path, or a previously established GraphQL node. The Server uses the current user token to prove user/App access and an App JWT to resolve the exact repository installation, then pins stable repository/installation IDs. It checks the requested read/write permission, suspension, connection version, and live execution again before use. Admission never enumerates a repository catalog. Code writes retain Session task-branch and PR restrictions. Configured Context Tree targets describe purpose; their default branch uses the existing verified Tree publication path.

## Invalidating access

GitHub authorization versions and credential generations serve different purposes. Scope changes, disconnection, and loss of authorization invalidate previously issued runtime access. A successful routine user-token refresh advances only the credential generation. Refresh and OAuth completion must compare the captured identity and version; a late response cannot reactivate a disconnected connection.

Refresh token consumption is not automatically retried after an uncertain response. A claimed refresh whose outcome is unknown requires reauthorization. A local credential-envelope failure is not an unknown outcome: nothing was sent to GitHub, so the claim releases untouched and the credential survives for a later retry. A periodic recheck that finds the access token already expired defers with a transient outcome; the refresh pass owns expiry recovery, and the expected 401 never clears a recoverable refresh credential. A credential-invalid response arriving at or after the access token's expiry defers the same way. A successful refresh also advances the recheck generation — never the authorization version — so a verdict minted against the old credential can never land on the new pair while runtime grants stay alive. Periodic rechecks scan all active due connections, including connections that received no webhook. Stale recheck results cannot overwrite a newer invalidation.

The default healthy recheck interval is five minutes. Worker scans and expired OAuth cleanup use batches of at most 100 rows. An expired OAuth sweep locks its bounded candidate set before clearing or deleting rows.

IM retains its existing generation field as a conservative authorization epoch. Authorization changes advance it; observations and heartbeats do not. Slack authorization depends on both the binding and its installation. Agent suspension, restoration, and placement changes also invalidate execution through the existing Agent revision fence.

## Encryption rollout

Application encryption supports the existing v1 format and an authenticated v2 envelope with a key ID and caller-supplied binding context. IM remains on v1 writes by default. Deploy compatible readers everywhere before opting into v2 writes; keep all required decryption keys until their ciphertext has been migrated or removed. Reverting to a binary that only reads v1 is unsafe after v2 writes begin.

Bound contexts distinguish credential purpose, owner, and stable record identity. Changing an envelope's record, owner, purpose, key ID, or authenticated content must fail authentication. New GitHub credentials require bound encryption. Platform secrets must not be included in logs or upstream error messages.

OAuth persistence accepts synchronous credential factories. The service allocates the final connection and flow IDs before invoking encryption. Replacing a GitHub user encrypts against the newly allocated connection ID inside the same transaction; failure rolls the replacement back. Factories must not perform network I/O, and provider token exchange happens before the completion transaction.

## Management and execution

Configure the coherent GitHub App environment block in `.env.example`, including the exact OAuth callback on `OPENTAG_PUBLIC_URL`. The existing Account GitHub section offers installation and refresh actions while the connection is active, including when personal, organization, or suspended installations already exist. The authenticated Server redirect resolves the configured App through GitHub and requires its App ID and OAuth client ID to match the deployment, with a safe App slug. Missing or mismatched metadata is rejected without redirecting. Installations therefore use that deployment's App without a separate setup page or App-slug setting. Installation opens in a new tab; refresh the existing section afterward to discover repositories. The link itself does not grant repository or Agent access.

Account refresh preserves focus, announces installation/repository counts and errors, and supports retry. It performs no configuration writes. Installation and refresh actions stay available when installations already exist.

The Account page connects, reauthorizes, replaces, or disconnects GitHub. Repository selection belongs to the GitHub App installation flow; OpenTag has no Agent assignments, repository delegation, or extra Account allowlist. The retired bindings route returns HTTP 410 and cannot change retained JSON. Discovery remains a bounded Account installation/refresh display, not an execution authorization source.

Every human sender accepted by an Agent's existing IM channel admission may request GitHub work using the Agent owner's Account connection, within that GitHub user's and App's permissions. This is intentionally broader than Account-owner-only IM access; the IM sender is not mapped to a separate GitHub identity, and no GitHub-specific sender or repository allowlist is maintained.

Configured schedules qualify only through Server-recorded execution provenance. Creation, edits and Agent resume capture the current fenced execution's source; dispatch freezes that source on the message. A scheduler origin alone grants nothing. Legacy/autonomous schedules without a traceable human root keep running without GitHub authority, and Account pause/resume does not upgrade their provenance. Already-dispatched work retains its snapshot after schedule changes or deletion.

Collaboration similarly requires exact Server-recorded provenance from a live fenced execution: the Session CLI passes its nonsecret execution ID alongside its existing Session proof, and the Server stores the source on the message. Local commands read the current execution marker from the stable provider environment file on every invocation, even when a provider runtime is reused across turns; Cloud publishes the same marker in its per-turn file. Missing current material never falls back to a stale inherited execution ID. Old/untraceable collaboration, bot ingress, bare Session identities, and validation probes receive no GitHub authority. Repository lists are absent from execution metadata and prompts.

Local peers negotiate `runtime.githubUserTask: 1`; Cloud Runners opt in with `githubUserTaskVersion: 1`. Older peers retain login, IM, recovery, and upgrade access but receive no new GitHub provider. Deploy Server first. Current GitHub requests lazily recheck target rights; routine UAT rotation does not revoke unchanged task authority.

The two runtime capabilities are `runtime.runtimeCredential` and `runtime.providerProxy`. Opening an execution binds Account, Agent revision, accepted task source, Session placement, current Computer connection, and Cloud Sandbox generation. A guessed Session ID or unrelated IM sender is insufficient. The broker rechecks these facts before issuance, renewal, each request, and during streams.

- A Runner capability lasts 60 seconds and renews after approximately 30 seconds. At most the current and previous capability overlap. Streams require an unexpired matching capability and revalidate every five seconds. GitHub additionally registers the actual repository admission for each active request, including snapshot preparation, response streaming and download-credit waits; loss of target permission cancels the stream and releases its IAT independently of Account connection health.
- The data WebSocket uses a single-use 15-second ticket in its first frame. Query strings, cookies, and bearer headers cannot authenticate this endpoint. Binary chunks carry at most 64 KiB plus a four-byte stream ID, with a 1 MiB credit window per direction. Consuming bytes replenishes credit. Completion races retain outstanding-byte bounds; unknown or reused stream IDs and over-credit frames remain invalid.
- The Runner holds capabilities in memory. CLI-visible material contains only execution-local handles, a public CA, proxy addresses, and bounded repository/IM metadata. No App key, UAT, IAT, Bot Token, tenant token, or Cloud control credential enters the Sandbox.
- IM proxy operations use registered Slack/Feishu routes and enforce the current binding and execution authority within the Bot's granted resource access. The current channel/thread is reply context, not an implicit exclusive destination allowlist. Every proxied write is one upstream attempt per proxy request, with no durable journal: JSON writes require both HTTP 2xx and explicit provider success evidence; explicit provider errors and definite 4xx (except 408) are rejections relayed to the caller; missing success evidence, 5xx, 408, timeout, transport failure, or an unparseable write response surfaces as an explicit `write_outcome_unknown` error. An ambiguous write is never automatically replayed — reconciling it against the platform is the task layer's responsibility, and a caller-initiated retry is simply a new proxied request. Upload-byte transfer is its own single-attempt write, separate from the provider's final attachment completion call.
- Local defaults to the existing IM credential mode. Set `OPENTAG_RUNTIME_CREDENTIAL_MODE=proxy` in the daemon launch environment to opt into proxy mode. Cloud requires proxy mode and never falls back to raw IM credentials.

Native command names and arguments remain `git`, `gh`, `slack api`, and `lark-cli`. The launcher supplies authentication, proxies, CA trust, configuration, renewal, and cleanup automatically. This preserves normal CLI operation within the granted repository and registered API surface. User-only OAuth commands, arbitrary provider admin operations, and commands outside the configured authority are rejected.

## Git and Context Tree

Git smart HTTP terminates at the trusted Server gateway. Reads use a bounded temporary repository snapshot. The Server stages the full receive-pack, checks the old ref, object integrity, fast-forward behavior, allowed refs and resource limits, then publishes atomically with expected-ref leases and confirms remote SHAs. IATs are scoped to one repository and explicit permissions, held only for their request, and revoked on request completion and execution closure. A revoke API response and a separately observed invalid-token response are distinct acceptance evidence.

Code writes use `refs/heads/opentag/<session-id>/code/`. Context Tree direct writes target the exact configured branch; Context Tree PR heads use `refs/heads/opentag/<session-id>/context_tree/`. Code reads cover all branches of the selected repository. Knowledge-only reads expose the configured Tree branch and that Session's work branches. Snapshot seeding never trusts remote ref-pattern matching as the authority: every ref the remote offers is re-filtered locally against the authorized exact refs and Session task prefixes before anything is fetched. Publishing Tree commits and opening/updating their PRs verifies the actual committed SHA using the pinned `@first-tree-ai/context-tree` verifier outside the Agent container. Gitlinks and symlinks are rejected except the verifier's canonical root `CLAUDE.md -> AGENTS.md` link.

Managed Context Tree preparation requires the execution-local transport even for cached results; the Server checks each actual repository request. Local and Cloud connect settings use Account-authenticated Server verification with a single-repository, read-only IAT and the pinned verifier. Creating a repository retains its existing capability boundary. Missing managed transport never falls back to host GitHub credentials. A Cloud host supplies a trusted Runner-side transport because container loopback addresses cannot be reused on the Runner.

**Resource limits.** Read snapshots and publication staging are bounded Server workspaces with fixed defaults: at most 4 concurrent read snapshots and 4 concurrent publications, a 120-second budget per operation, and a 512 MiB workspace cap each. A receive-pack request may carry at most 64 MiB of pack data; an upload-pack request body is limited to 1 MiB and its streamed response to 512 MiB. Object validation after staging runs over the whole staged repository — the seeded history plus the received pack — never over the incoming pack alone: at most 100 000 objects in total, at most 64 MiB per object, and at most 512 MiB of uncompressed object data in total, with `git fsck --strict` covering the staged repository including its seeded history. A repository whose seeded history exceeds these totals cannot be published to through the gateway. These are deliberate current constraints of the bounded staging design and apply to the seeded history, the incoming pack, and the received objects alike.

The GitHub API proxy parses REST routes and GraphQL ASTs, including aliases, fragments, variables and node identities. PR mutation checks repository, Session-owned head and allowed base. Tree-only queries are constrained to the configured Tree base. There is no generic GitHub API forwarding, arbitrary Git-object write endpoint, merge permission, or branch-protection bypass.

## Deployment and persistent state

`createPlatformRuntime` is the Server assembly entry. The Server image includes Git and the pinned Tree verifier. PostgreSQL is the only persistent integration state: GitHub connections and IM credentials recover from the database across a Server rebuild. There is no Server-local control volume, no file-backed write journal, and no separate persistent source ledger — rebuilding a Server never requires restoring an integration-specific disk. Short-lived capabilities, tickets, IAT leases, URL handles, and execution state live in bounded Server memory and end with the process; after a restart the Runner re-authorizes from current database facts. A restart does not itself revoke already-issued platform tokens: installation tokens simply stop being used and expire under GitHub's own rules.

Git read snapshots, publication staging, and Tree verification workspaces are private bounded temporary working directories. When GitHub transport is enabled, the gateway lazily creates one exclusive `mkdtemp` root under the OS temporary directory on first use, verifies its ownership and mode, and removes it on close or partial-construction failure. These ephemeral workspaces are verification aids, never authoritative state; nothing is written to the filesystem while GitHub integration is disabled, and temporary directories are never mounted into a Sandbox.

User-task provenance in Session messages and schedules is ordinary PostgreSQL task state. Cross-restart provider-operation ledgers and provider-result provenance tracking are explicitly withdrawn. The proxy performs one upstream write attempt per request and classifies the response in memory as succeeded, definitely rejected, or unknown; it does not promise persistent cross-restart resource blocking or exactly-once provider effects. If a product requires remembering an unresolved write across a crash, that is durable business state that must be modeled explicitly in PostgreSQL with real ownership and retention semantics, never a sidecar file store.

Cloud control identity belongs to Computer/Cloud orchestration; its integration with this credential runtime remains to be wired. The integration runtime only consumes an explicitly injected trusted verifier and activity checker (`TrustedCloudControlAuthority`): it keeps the credentialId/computerId/installationId binding, the current database Computer identity (`kind = 'cloud'` with the live installation identity), and per-request revocation checks. The current default startup injects no trusted Cloud control verifier or activity checker, so Cloud control authentication and Cloud credential activity are rejected; Local keeps its existing machine-token path and its Local-only restriction. There is no implicit self-issued Cloud credential, no Local-token fallback, and no additional file-backed Cloud credential database beyond the PostgreSQL-managed integration credentials. Executions remain bound to their exact current control connection; this correction does not provide stateless multi-node execution routing.

`CloudSandboxCredentialBridge` is the Linux command boundary for the Cloud orchestrator. It creates the Relay outside the command container and mounts only a public per-execution socket directory plus the workspace. The container runs as UID 10000 with no external network, no capabilities, a read-only root, resource limits and writable temporary directories. Control loss kills the command container; an execution cannot be replayed. It requires a trusted Linux Docker controller; a macOS host socket bind is not equivalent. The bridge supports later Cloud Sandbox orchestration and does not provision a cloud service or an LLM network path itself.

## Acceptance boundaries

Local checks must include protocol/authorization tests, PostgreSQL migration and authority tests, native CLI calls through the actual Relay/proxy stack, rejection and cancellation cases, and inspection of Sandbox-visible material. Live GitHub acceptance additionally requires the configured App, installation permissions and selected test repository; OAuth/UAT admission and real PR operations must be verified separately from an IAT-only Git test. Live IM acceptance requires an explicitly selected test Bot and conversation, including authorization for any outbound test messages or files. Offline provider fixtures cannot establish real-account acceptance. Production deployment and release require their own verification.
