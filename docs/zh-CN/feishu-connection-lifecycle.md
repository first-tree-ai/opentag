# 飞书连接生命周期

[English](../feishu-connection-lifecycle.md)

飞书设置在现有 IM 绑定上保留一个持久授权尝试。注册 SDK 返回应用凭据后，Server 先保存，
再检查激活条件。企业管理员可以稍后审核；刷新、关闭页面或 Server 重启都不应丢弃已保存的授权。

## 用户体验

继续要求 `FEISHU_REQUIRED_TENANT_SCOPES` 中全部 66 项权限，不提供部分权限模式或后续能力升级。
启动注册前仍须完成现有 Computer 与 Runtime 准备。

凭据保存后，页面展示尚未满足的条件：权限、应用可用性、Runtime 就绪或上游暂时失败，
并告知用户可以关闭页面。企业审核由管理员在飞书中处理；OpenTag 不代为提交审批，
也不要求连接用户本人是管理员。

Server 自动检查。“检查最新状态”共用自动检查的时间与并发限制，不新建应用、不绕过审批、
不强制重复调用供应商。“取消连接”明确删除待处理授权；关闭已保存授权的弹窗会保留它。
二维码阶段继续遵守短期注册规则。

新连接只有在全部权限、身份、应用和 Runtime 检查及现有激活事务成功后才可用。
同一应用重新授权期间，原有健康连接可以继续收发消息。取消该授权不得清除原工作凭据或改变其代次。

## 现有实体与职责

| 现有数据 | 职责 |
| --- | --- |
| Account / Agent | 管理绑定的权限；Computer 和 Runtime 前置条件 |
| `im_bindings` 状态与活动身份 | 当前消息路由；候选凭据不覆盖它 |
| 工作凭据密文 / generation | 现有凭据分发与消息连接并发保护 |
| 设置尝试 ID / intent | 绑定上当前唯一的 create、reauthorize 或 replace 尝试 |
| 设置上下文密文 | 旧二维码数据或带版本的候选凭据与最近观察 |
| 设置期限 | 发放前为二维码期限；保存后为固定候选保留期 |
| 设置 owner / heartbeat | 二维码实例所有权，或每轮检查新建的领取令牌 |
| 飞书注册与平台 API | 发放凭据、观察已生效权限与机器人身份 |

不引入审批记录、管理员角色、连接流程表、重试表、候选路由或额外凭据代次。
换应用继续使用现有替换事务与历史关系。

## 状态与数据契约

`awaiting_user` 保存二维码上下文。凭据发放后进入 `pending_activation`，保存候选密文并清除 owner。
获准执行的检查领取为 `validating`；可恢复结果回到 `pending_activation`。
成功激活或终止时清除临时凭据；取消、停用和到期同样清理。

候选固定保留 30 天，与二维码期限独立；重复检查不延长期限。保留期不提供部署配置项，
仅测试通过构造函数注入不同取值。过期或明确无效的凭据需要重新授权，不能从 App ID 或状态修改中还原已丢弃的 Secret。

候选具有版本和严格校验，解密后核对绑定与尝试 ID。
内容仅包括 App ID、Secret、区域、保存与下次检查时间，以及最近一次有限原因和缺失权限清单。
公开 DTO 只返回 App 标识和观察，不返回 Secret、密文或领取令牌。未知格式不作为可执行候选。

现有凭据加密支持 v1，以及带上下文 AAD 的 v2；使用 v1 时仍须核对候选内的身份字段。
本功能不改变全局加密写入版本，不批量重加密历史凭据。

### 最小数据库迁移

- 给 `feishu_setup_state` 追加 `pending_activation`。
- 扩展 `im_bindings_setup_owner_shape`，允许非 disabled 的飞书绑定保存无 owner 候选，
  且 attempt、intent、context、expiry 必须完整。
- 对旧状态（包括 NULL）保留原约束分支。
- 不新增表、列或索引，不回填客户数据。

加密 JSON 扩展仍属于真实的数据契约变更。PostgreSQL 无法校验解密内容，服务层必须承担格式与身份校验。

## 恢复与并发

复用设置服务定时器，按主键游标分批扫描候选，根据已保存的下次检查时间准入，
限制并发、加入抖动并遵守供应商 `Retry-After`。手动 POST 检查共用准入；GET 只读。

领取时同时比较绑定、尝试、状态、原密文与期限。每轮检查在已有 owner 字段写入新的随机令牌。
心跳、观察、释放和激活必须匹配该令牌；旧进程不能覆盖新领取者、已取消尝试或已停用绑定。
关闭服务时保留已保存凭据，供后继进程恢复。

候选打开消息通道前须满足全部 66 项权限；只有就绪候选进入现有原子激活。
不明确的上游错误保留候选；供应商明确的 Secret 无效与通用参数错误、应用停用分别处理。

这是使用现有字段的数据库恢复循环，不是与飞书之间的 exactly-once 事务。
外部发放凭据到首次提交数据库之间崩溃，仍可能丢失新 Secret。
本次不增加调度索引，大量候选也会带来扫描与解密成本。

## 发布与回退边界

仅执行迁移不会让旧 Server 理解新状态和上下文。采用协调的非重叠 Server 切换：
停止全部旧设置写入者，执行迁移，再启动新 Server 和配套 Web。这是硬性切换而非滚动混部：
旧 Server 不认识 `pending_activation`，可能用新的二维码尝试覆盖无 owner 的已保存候选，
也无法渲染新状态。无论是否已存在新候选，都不得并发混跑新旧 Server 写入者。
迁移遵守现有 journal、snapshot 与 hash 校验流程，并按部署规模检查锁持有时间。

发布须同时包含配套 CLI。本地凭据模式仅在启用代理执行路径时声明代理能力；否则 Server
可能选择本地运行时无法执行的校验流程。Server、Web、CLI 制品均包含各自修复，且本地
已安装的新 CLI 完成重连后，才能宣称连接修复发布完成。

回退须使用理解新枚举和加密上下文的兼容构建，保留安全展示、取消及过期清理能力。
不能删除枚举或迁移账本，也不能为启动旧程序清除有效客户凭据。
生产迁移、部署和真实管理员审核验收与本地测试是不同阶段。

此前已经丢失 Secret 的旧尝试，不能靠修改为 active 恢复；必须通过供应商重新授权原应用。
新保存的候选在实际前置条件生效后可自动恢复。
